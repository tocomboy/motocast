# 버전과 업데이트 소식

## 버전 번호

MOTOCAST는 [Semantic Versioning 2.0.0](https://semver.org/lang/ko/)을 바탕으로 `주.부.수` 세 자리 버전을 사용합니다. 현재 버전의 정본은 `package.json`의 `version`이며 `package-lock.json`과 최신 업데이트 항목도 같은 값이어야 합니다.

- 호환되지 않는 공개 API·저장 데이터·사용 방식 변경: 주 버전을 올립니다. 이전 데이터와 클라이언트의 전환 방법을 먼저 정합니다.
- 기존 사용 방식을 유지하는 기능 추가: 부 버전을 올리고 수 버전을 0으로 돌립니다.
- 호환되는 오류 수정: 수 버전을 올립니다.
- `0.x`는 초기 개발 단계입니다. 이 단계에서는 기능 추가와 호환되지 않는 변경 모두 부 버전을 올리되, 호환되지 않는 변경은 전환 안내를 반드시 기록합니다. `1.0.0`은 별도의 안정성·제품 완료 판단 후 정합니다.
- 문서·개발 도구만 바뀌어 실행 결과가 같으면 버전을 올리지 않습니다. 이미 릴리스한 버전의 제품 내용이나 태그를 덮어쓰지 않습니다. 수정된 실행 코드를 다시 배포할 때는 새 버전을 사용합니다.

이번 `0.2.0`부터 이 규약을 적용합니다. `0.1.0` 항목은 기존 패키지 버전으로 제공하던 2026-09-15 운영 기능의 사후 요약입니다. 과거에 버전 태그나 정식 Release가 있었다는 뜻은 아닙니다.

## 사용자가 보는 내용

`lib/releases.ts`는 최신순 업데이트 소식의 정본입니다. `/updates`와 첫 접속 안내가 같은 현재 버전 요약을 사용합니다. 각 항목은 버전, 한국 날짜, 짧은 제목·설명과 주요 변화 2~4개로 구성합니다.

“무엇을 할 수 있게 됐는지”, “어떤 불편이 줄었는지”를 설명합니다. 커밋·파일·PR·내부 운영 기록·전체 작업 목록은 노출하지 않습니다. 새 기능을 실제 제공 전에 제공 중이라고 기록하지 않습니다. 사용자 영향이 없는 내부 수정은 생략할 수 있습니다. 저장된 코스·공유 링크·사용 방식에 영향을 주는 변경은 필요한 행동과 함께 반드시 알립니다.

화면 아래 현재 버전 링크에서 언제든 업데이트 소식을 다시 열 수 있습니다. 공개 업데이트 페이지에는 정적 제품 요약만 담으며 계정·라이딩 데이터에 접근하지 않습니다. Preview에서 보이는 현재 버전은 그 Preview 배포의 버전이며 Production 배포 완료를 뜻하지 않습니다.

## 사용자별 첫 접속 안내

활성 회원이 새 버전의 계획 화면 또는 초대 관리 화면에 처음 접속하면 현재 버전의 핵심 변화만 팝업으로 표시합니다. 로그인·공유·업데이트 페이지에는 자동 팝업을 띄우지 않습니다. 닫기 버튼, 확인 버튼, Escape로 닫을 수 있고 작은 모바일 화면에서는 팝업 내부를 스크롤할 수 있습니다.

`public.release_announcements`는 사용자 ID와 버전을 기본 키로 저장합니다. 기록은 브라우저 저장소가 아니라 각 환경의 DB에 있으므로 같은 계정의 다른 기기·브라우저·동시 탭에서도 중복 안내를 막습니다. 다른 사용자는 독립적으로 안내받습니다. Preview와 Production의 확인 기록은 공유하지 않습니다.

서버의 `POST /api/releases/claim`은 같은 출처의 JSON 요청과 실제 로그인 신원을 확인하고, 현재 배포 버전을 고정해 `claim_release_announcement`를 호출합니다. 요청의 `expectedVersion`은 현재 화면과 서버 버전이 같은지 비교하는 조건일 뿐, 기록할 버전을 선택하는 권한이 아닙니다. 오래된 탭의 버전이 다르면 기록 전에 409로 거절하고 새로고침을 안내하므로 신버전 안내를 소모하지 않습니다. 사용자가 다른 사람의 ID를 지정할 수 없습니다. DB 함수는 활성 회원의 자기 기록만 원자적으로 생성하며 테이블 직접 읽기·수정은 허용하지 않습니다. 확인 기록은 회원 가입이나 역할 부여 권한으로 사용하지 않습니다.

최초 표시 예약 시 기록합니다. 한 화면의 응답 손실 재시도는 같은 표시 ID로 결과를 재생하고, 다른 화면의 새 요청은 이미 표시 예약된 것으로 처리합니다. 화면이 닫히거나 네트워크가 끊어진 바로 그 순간까지 사람이 실제로 읽었음을 증명하지는 않습니다. 실패 시 사용 가능한 업데이트 링크와 재시도를 제공하며, 페이지 재방문으로 기록을 지우거나 자동 안내를 반복하지 않습니다. 계정 삭제 시 해당 기록도 삭제됩니다.

## 변경과 배포 순서

1. 배포 단위의 가장 큰 사용자 영향을 기준으로 버전을 정합니다. 패키지·lockfile·업데이트 데이터와 회귀 검증을 같은 변경에 반영합니다. 과거 버전 사이에 임의의 번호를 끼워 넣지 않습니다.
2. 버전 일치·순서·날짜 검사, 페이지·팝업 모바일/키보드/중복 표시 검증, 실제 DB 소유권·동시성 검증 및 [기존 필수 검사](verification-and-review.md)를 완료합니다. 정상·오류·미실행 증거를 구분합니다.
3. `review-* -> develop` PR의 검증된 고정 SHA와 배포 없음 증거를 확인합니다. DB 변경이 있으면 동일 후보의 추가 migration을 Preview에 먼저 적용·검증한 뒤 동일 SHA를 develop에 반영합니다.
4. Preview에서 현재 버전·새 화면·표시 상태와 영향받은 제품 경로를 확인한 뒤 같은 저장소의 `develop -> main` PR로 승격합니다. Production DB의 추가 migration을 웹 승격 전에 적용합니다. 기존 승인 경계와 필수 제품 검증은 유지합니다.
5. Production의 실제 배포 SHA·주소·버전·페이지·팝업 동작·보안 헤더를 확인합니다. 성공한 main 커밋에 `vX.Y.Z` 태그를 만들고 같은 사용자 요약으로 GitHub Release를 작성합니다. 자동 커밋 목록을 사용자 변경 요약 대신 게시하지 않습니다. 과거 태그를 이동하거나 강제 push하지 않습니다.

이 변경의 migration은 기록 테이블과 함수만 추가합니다. 기존 사용자·코스·날씨·공유 데이터는 변환하지 않습니다. 웹 복구가 필요하면 이전 검증된 main 버전을 사용하는 새 승격 PR을 준비하고, 추가 테이블과 확인 기록은 유지합니다. DB 삭제나 역방향 migration은 복구에 필요하지 않습니다.

릴리스 성공과 전체 제품의 운영 수용 조건은 별도로 보고합니다. 기존의 다른 계정·신규 초대·권한 회수 등 미완료 검증을 이번 버전의 화면 검증으로 대체하지 않습니다.
