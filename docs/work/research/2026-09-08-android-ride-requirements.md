# Android 주행 지원 및 음식점 추천 — 추후 개발 요구사항

- 기록일: 2026-09-08
- 근거: 이 작업의 사용자 브레인스토밍 및 요구사항 기록 요청.
- 상태: 요구사항 합의 기록. 구현·배포·성능 검증 완료를 뜻하지 않는다.
- 현재 제품 정본: [MOTOCAST_SOT.md](../../product/MOTOCAST_SOT.md).
- 적용 시 검증 규범: [verification-and-review.md](../../rules/verification-and-review.md).
- 이 문서는 향후 개발 범위이며 현재 배포 제품의 동작을 소급해 변경하지 않는다. 구현 전 관련 제품 결정과 연결하고 충돌하는 범위는 기존 결정 절차로 처리한다.

## 1. 범위와 우선순위

핵심 범위는 Android 앱의 주행 중 위치 기반 날씨 안내와 음식점 추천이다. Android 앱은 Kotlin + Jetpack Compose로 개발한다. iOS는 초기 개발 범위에 포함하지 않는다.

백엔드는 현재 TypeScript/Supabase를 유지하고 앱과 명확한 API 계약으로 분리한다. 앱은 GPS·화면·주행 상태·기기 알림을, 백엔드는 인증·권한·경로·추천·날씨·저장·호출 예산을 담당한다. API 요청/응답·오류·버전 호환을 문서화하고 서버용 비밀키를 앱에 포함하지 않는다. 기존 DB 접근 보호 규칙과 좁은 서버 쓰기 경계를 유지한다.

Kotlin 백엔드 전환은 별도 장기 검토 항목이다. Android 전환의 선행조건이나 필수 완료 조건이 아니며, 측정된 제약·운영 비용·이식 위험을 근거로 추후 판단한다. 초기 저장소는 앱·백엔드·API 명세를 논리적으로 분리하고 각각의 빌드·배포 경계를 둔다.

관광지 추천은 최하위 선택 항목이다. 핵심 요구사항과 필수 품질·운영 작업을 모두 마친 뒤 여력이 있을 때만 검토한다. 핵심 개발의 완료 조건이나 선행 의존성에 포함하지 않는다. 관광지의 추천 방식과 운영시간 처리는 실제 착수 시 구체화한다.

## 2. 사용자 규모와 확장성

- 초기 전체 사용자 최대 20명, 하루 주행 사용자 최대 10명.
- 하루 사용자 전원인 최대 10명의 동시 주행·요청을 초기 검증 기준으로 삼는다.
- 사용자 수·API 호출 예산·갱신 주기를 코드에 고정하지 않고 설정으로 관리한다.
- 위치/도착 시간 계산, 날씨 조회, 알림, 외부 API 연동의 책임을 분리한다.
- 같은 지역·예보 시간대 데이터는 공유하고 중복 요청을 통합한다.
- 향후 서버가 여러 개가 되어도 호출 예산과 단계별 알림 이력을 일관되게 관리한다.
- 사용자당 호출량, 캐시 재사용률, 응답 시간, 갱신 지연을 측정해 확장 시점을 판단한다.
- 초기부터 다중 서버를 운영한다는 뜻은 아니다. 유료 API·자동 과금은 별도 승인 없이 활성화하지 않는다.

## 3. 주행과 위치 확인

2026-09-18 확정 보완: 라이딩 요약의 `경로 실행`을 주행 시작 진입점으로 사용한다. 소유자 요약은 최신 계산 결과, 공유 요약은 저장·새 일정 생성 없이 유효한 공유 장소·방문 순서를 사용하며 공유 당시 시간·날씨를 현재 주행 결과로 취급하지 않는다. 경유지 제한·카카오맵 설치·위치 권한을 확인하고 안전 안내를 받은 뒤, MOTOCAST가 전면에 있을 때 GPS 추적과 주행 알림을 시작하고 카카오맵 경로 화면을 연다. 설치 안내 중에는 추적하지 않고, 외부 앱 실행 요청 실패 시 그 시도에서 새로 시작한 주행만 정리한다. 중복 탭으로 기존 주행을 중복 생성하거나 종료하지 않는다. 위치 서비스가 시작된 것과 카카오맵 길안내가 시작된 것은 별도 상태다. 웹/PWA 공유본 직접 실행에는 GPS를 추가하지 않으며, 네이티브에서 공유 코스를 주행 세션과 결속하는 세부사항은 이 Android 작업에서 검증한다. [정본 ROUTE-008](../../product/MOTOCAST_SOT.md#route-008--execute-the-summarized-course-in-kakaomap), [웹 연동 계획](2026-09-18-kakaomap-handoff-plan.md), [Android #31](https://github.com/tocomboy/motocast/issues/31).

- 사용자가 주행을 시작한 때부터 최종 목적지까지를 하나의 주행으로 본다.
- 앱 안과 상태바를 내려 여는 알림 영역에서 주행 시작·종료를 제공한다.
- 다른 앱을 보거나 화면을 끈 상태에서도 주행 중 위치를 확인하고 필요한 날씨 알림을 제공하는 것을 목표로 한다.
- 식당·휴식 경유지 도착만으로 주행을 끝내지 않는다. 최종 도착 시 자동 종료와 사용자 직접 종료를 제공한다.
- Android 권한, 백그라운드 실행, 절전, 알림 영역에서의 시작 동작은 기기 검증이 필요한 항목이다.
- 내비에서 다른 길을 선택해 경로를 이탈하면 현재 위치에서 남은 경유지를 순서대로 방문하는 기준으로 도착 시간과 날씨를 갱신한다.
- 경유지를 자동 삭제하지 않는다. 사용자가 '건너뛰기'를 선택한 경유지만 남은 일정에서 제외한다.

## 4. 일정과 체류 시간

사용자가 입력하는 시간은 출발 시간이다. 최종 도착 희망 시간·마감 시간은 입력받지 않고 예상 도착 시간을 계산한다. 도착 희망 시간 초과에 대한 지각 경고는 제공하지 않는다.

| 경유 유형 | 기본 체류 시간 | 수정 |
| --- | --- | --- |
| 도로상 통과 경유지 | 0분 | 식사·휴식 체류 규칙에서 제외 |
| 점심·저녁 | 60분 | 가능 |
| 휴식 | 30분 | 가능 |

- 도착 전에는 설정한 체류 시간을 이후 도착 시간 계산에 반영한다.
- 도착 후 예정 출발 시간을 넘기면 지연된 만큼 이후 도착 예정 시간을 보정한다.
- 일찍 출발하면 실제 출발을 기준으로 다시 계산한다.
- 보정 결과를 이후 구간 날씨와 음식점 방문시간 경고에 함께 반영한다.
- 도착·출발 자동 감지 방식과 오인식 보정 UI는 미확정이다.

## 5. 날씨 갱신과 강수 알림

- 현재 GPS 위치와 경로 구간별 예상 통과 시간을 기준으로 날씨를 판단한다.
- 비 예상 구간 진입 90분·60분·30분 전에 총 세 차례 알림을 제공한다. 세 값 중 하나를 선택하는 방식이 아니다.
- 기본 알림은 소리·진동이며, 사용자가 알림 방식을 선택할 수 있다.
- 동일 단계의 중복 알림을 방지한다. 주행 시작 시 이미 가까운 구간이면 지난 단계 알림을 몰아서 보내지 않는다.
- 강수 구간과 예상 시각을 안내한다. 비 회피 우회 경로·대체 경로 제안은 범위에서 제외한다.
- GPS/도착 시간 갱신, 외부 날씨 조회, 알림 판단을 분리한다. 알림마다 외부 날씨 API를 호출하지 않는다.
- 캐시 및 중복 요청 통합으로 외부 호출을 절감한다.
- 남은 호출량과 한도 초기화 시각을 기준으로 소진을 예측하고, 필요하면 갱신 간격을 단계적으로 늘린다.
- 현재 주행 중이고 곧 통과할 구간을 우선 갱신한다.
- 내부 안전 예산을 넘는 외부 호출을 제한한다. 한도 또는 갱신 실패를 '비 없음'으로 처리하지 않는다.
- 마지막 갱신 시각과 예보가 오래되거나 갱신이 지연된 상태를 표시한다.
- 구체적인 갱신 간격·안전 여유분은 호출량과 제공처 한도 확인 후 결정한다. 대화의 10/20/30분은 설명용 예시이지 확정값이 아니다.
- 강수 판단 기준, 예보 변경/취소 시 알림 정책, 여러 강수 구간을 묶는 기준은 미확정이다.

## 6. 음식점 추천

- 경로와 식사 시간에 맞는 음식점을 추천하고 사용자의 직접 추가도 허용한다.
- 식사 경유지를 자동 추가하지 않고 사용자가 선택한다.
- 기본 우회 허용 범위는 추가 주행 30분이며 수정 가능하다. 체류 시간과 추가 주행 시간은 구분한다.
- 점심 추천 시간대 초기값은 11:00~15:00, 저녁은 17:00~20:00이며 수정 가능하다.
- 방문 시간이 맞지 않아도 이유를 표시하고 선택을 허용한다.
- 브레이크 타임 시작 30분 전 도착부터 브레이크 타임 종료 전까지 경고한다. 식사 60분 전체를 확보하지 못했다는 이유만으로 별도 경고하지 않는다.
- 영업 종료 30분 전부터, 라스트오더 시각부터 경고한다. 휴무·영업시간 밖 도착도 안내한다.
- 경고에는 아래 순서로 모든 항목을 표시한다. 확보되지 않은 정보는 '정보 없음'으로 구분하며 경고가 없다는 이유로 영업 가능하다고 단정하지 않는다.

1. 도착 예정 시간
2. 브레이크 타임
3. 라스트오더
4. 영업 종료 시간

## 7. 응답 시간 요구사항

| 기능 | 시작 | 실제 완료 기준 | 목표 |
| --- | --- | --- | --- |
| 경로 생성 | 생성 버튼 클릭 | 지도 경로와 예상 도착 시간 표시 | 5초 이내 |
| 음식점 추천 | 추천 요청 | 선택 가능한 첫 목록과 추가 주행 시간·도착 예정·영업정보·관련 경고 모두 표시 | 3초 이내 |

- 로딩 화면·빈 화면·필수 정보가 빠진 목록은 완료가 아니다.
- 운영시간 원천 데이터가 없는 경우에는 명시적인 '정보 없음' 상태를 포함한다. 단순 조회 지연을 데이터 없음으로 위장하지 않는다.
- 캐시 없는 최초 요청과 최대 10명 동시 요청을 검증에 포함한다.
- 외부 API 지연에 따른 목표 초과도 기록하며, 임의 경로나 허위 영업정보로 시간을 맞추지 않는다.
- 관광지 추천을 추후 실제 개발할 경우에도 첫 목록과 판단에 필요한 정보를 3초 이내 표시하는 목표를 적용한다. 현재 핵심 완료 조건에는 포함하지 않는다.
- 단말·네트워크 조건, 측정 구간과 반복 횟수, 허용 실패율/백분위 기준은 구현 전 명문화한다. 현재 5초·3초 목표를 입증한 측정은 없다.

## 8. API 조사 결과와 미해결 조건

2026-09-08 대화에서 현재 코드와 공식 공개 문서를 확인했다. 계정 콘솔의 실제 적용 한도·남은 사용량은 미확인이다.

| API | 공개 무료 한도 |
| --- | --- |
| 기상청 API허브 일반회원 | 하루 20,000건 및 5GB |
| 카카오 자동차 길찾기 | 하루 10,000건 |
| 카카오 미래 운행 정보 길찾기 | 하루 5,000건 |
| 카카오 키워드/카테고리 장소 검색 | 각각 하루 100,000건 |
| 카카오 지도 Web / Android·iOS SDK | 각각 하루 300,000건 |

- 카카오는 전체 API 월간 무료 300만 건 등 공통 한도와 권한 조건도 적용한다. 무료 한도는 변경 가능하므로 구현 전 다시 확인한다.
- 현재 코드는 기상청 초단기/단기예보, 카카오 현재/미래 길찾기, 키워드 장소 검색을 사용한다.
- 경로 생성 한 번이 외부 호출 한 번이라는 보장은 없다. 경로 분할·후보별 우회 계산·재계산을 예산에 포함한다.
- 날씨도 경로의 지역 수와 모델에 따라 여러 번 조회할 수 있다. 개발·테스트 예산과 전송량도 포함한다.
- 카카오 공개 장소 검색 응답에는 영업시간·브레이크 타임·라스트오더·평점·리뷰가 없다. 상세페이지 링크 제공은 해당 데이터를 API로 제공한다는 뜻이 아니다.
- 음식점 운영시간의 별도 데이터원 또는 사용자/관리자 입력과 검증 방법을 조사해야 한다. 자동 확보 가능성은 미검증이며 추천 품질 기준도 미확정이다.
- 외부 API 무료 범위와 서버·DB·배포 비용은 별도다. 초기 인원 수용 능력과 전체 무료 운영은 아직 검증하지 않았다.

- 핵심 하위 과제: [#30 API 기반](https://github.com/tocomboy/motocast/issues/30), [#31 주행 지원](https://github.com/tocomboy/motocast/issues/31), [#32 날씨·알림](https://github.com/tocomboy/motocast/issues/32), [#33 음식점](https://github.com/tocomboy/motocast/issues/33), [#34 성능·무료 예산 검증](https://github.com/tocomboy/motocast/issues/34).
- 별도 선택 과제: [#35 Kotlin 백엔드 검토](https://github.com/tocomboy/motocast/issues/35), [#36 최하위 관광지 옵션](https://github.com/tocomboy/motocast/issues/36). 핵심 상위 Issue의 필수 하위 과제로 연결하지 않는다.
- 이번 변경은 요구사항 문서와 사용자가 승인한 GitHub Issue 생성·연결에 한정한다. 모든 Issue는 백로그이며 자동 실행 Goal을 생성하지 않는다.
- 신규 기능 구현, API 실호출, 부하/성능 테스트, Android 기기 검증: NOT_RUN. 문서 PR의 기존 코드 회귀 검사 결과는 해당 PR과 CI에서 별도로 기록한다.
- 세션 종료 요청에 따라 이 문서만 분리해 커밋·푸시·develop 대상 PR로 관리한다. 기존 제품 정본 및 작업 중 파일은 보존한다. develop 반영에 따른 Preview 자동 배포와 Production 승격은 구분하며, Production 승격은 이번 범위에 포함하지 않는다.
- Notion 동기화는 미수행이다. 이 저장소에서 `docs/notion-project-tracking.md` 연결 문서를 찾지 못했으며 관리 대상 Notion 프로젝트도 이 작업에서 확인하지 못했다. 로컬 기록을 정본 근거로 보존하고 외부 기록은 대기로 남긴다.
