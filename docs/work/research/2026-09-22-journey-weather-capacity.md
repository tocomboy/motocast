# 주행 날씨 저장 용량 상한과 활성화 준비

사용자의 후속 `진행해`에 따라 정상 예산·저장 상한·접근 경계 검증을 진행한다. 기존 자동 정리는 완료됐고 Preview 최근3회 예정 실행 succeeded, 전체 DB23,309,459 bytes다. 이번 시작 시 원본 develop 원격을 fetch하고 기존 dirty 파일과 clean review 작업 트리를 확인했다.

1. 완료: 저장 상한 구현. 예산이 소진된 뒤 claim만으로 새 식별 행이 쌓이거나 정리 job이 멈춘 경우를 제한한다.
2. 완료: PR용 격리 작업 트리의 독립 DB에서 권한·계획·공유 기준선321 PASS, 캐시12 PASS, 정리12 PASS, 용량11 PASS, 기존 ready/fetching 행이 있는 DB의 migration 1 PASS. 루프백 실제 요청/timeout 2 PASS, Node20 단위687 PASS, lint/typecheck/빌드/Deno check PASS, Chromium49 PASS·기존 연결 검사2 SKIP.
3. 진행: 기상청 계정 한도·사용 현황을 직접 재확인했다. 정확한 변경 파일과 복구안을 확정해 게시/Preview 적용을 준비한다. 활성화에 필요한 Preview 회원·공유 실경로 검증은 아직 NOT_RUN이다.

현재 사용자 승인은 후속 구현·검증이며 기존 게시 승인은 이전 고정22/8파일에 한정됐다. Preview 주행 활성화·예산 증액·추가 파일 공개 게시와 Production 변경은 이 준비 문서로 대신 승인하지 않는다.

## 확인한 위험과 설계
- 외부 호출 예산은 `start`에서 확보되지만 새 캐시 행은 `claim`에서 먼저 삽입된다. 따라서 호출 일일 예산만으로 캐시 행 수를 제한할 수 없다.
- 자동 정리는 유효기간·보존 기간을 관리하지만 정리 장애 시 저장 상한이 아니다. SQL 크기 측정은 데이터/인덱스 공간이며 WAL·시스템 파일을 포함한 전체 디스크와 구분한다.
- 기존 budget policy에 설정 가능한 보수적 상한을 추가한다: 캐시 식별10,000행, 상세 시도10,000행, 활성 예보 및 실행 중 응답 예약64MiB, 캐시·시도 물리 relation128MiB, 전체 DB250,000,000bytes. 기술적 초기 보호값이며 처리량 보장이 아니다.
- 외부 요청 시작 전에 최대 응답1MiB를 캐시 용량에도 예약한다. 실제 본문은 검증된 JSON 크기로 계산하며 실패/unknown 호출 예산은 환불하지 않는다. 기존 유효 캐시 적중은 저장 차단 중에도 허용한다.
- `storage_bytes` 생성 열이 본문 길이 또는 실행 중 예약을 자동 계산한다. 합계 조회마다 전체 JSON을 압축 해제하지 않으며, 본문 제거/실패에 따라 0으로 바뀐다. 정책 상한을 낮춰도 이미 확보한 예약 안의 완료는 허용한다.
- 기존 budget advisory lock을 캐시 함수 시작부터 같은 순서로 사용한다. 임계치 판정과 새 행/예약을 직렬화하고, 만료/실패/정리처럼 공간을 줄이는 변경을 막지 않는다.
- 전체 DB 측정은 다른 기능의 동시 쓰기나 WAL을 원자적으로 제한하지 않는다. 캐시가 크게 성장하기 전에 중단하는 보호선이며 Supabase 전체 용량 제한을 대신하지 않는다. 임계치 도달 시 날씨 확인 불가를 반환하고 정리/운영 점검을 요구한다. 자동 증액이나 유료 플랜 전환은 하지 않는다.

## 정상 배정 계산과 남은 조건
API허브에서 재확인한 계정 한도20,000회/5GB와 Preview10% 배정이면2,000회/500,000,000bytes다. 현재 1MiB 사전 예약은 약476회/일까지 허용하므로 호출 수만 보고2,000회를 보장하면 안 된다. 이 계산값은 적용하지 않는다. 현재40회/40MiB와 비활성 상태를 유지한다.

공식 근거: [Supabase DB와 디스크](https://supabase.com/docs/guides/platform/database-size)는 Free DB500MB 제한과 WAL/디스크 구분, 삭제 즉시 파일 크기가 줄지 않는 점을 설명한다. 실제 프로젝트 플랜과 다른 환경까지 확인된 것으로 확대하지 않는다.

## 이번 확인과 적용 경계

2026-09-22 API허브 마이페이지에서 한도와 그 시점 사용 현황을 직접 확인했다. 계정별 사용량·키·화면 원본은 공개 변경에 기록하지 않는다. Preview 원장의 예약량은 실제 수신량보다 보수적이므로 공급자 화면 값으로 원장을 낮추거나 환불하지 않는다.

2026-09-23 Preview 읽기 전용 확인: `ACTIVE_HEALTHY`, migration head `20260922083416`, 캐시3행·시도6행, 해당 두 relation131,072bytes, 전체 DB23,366,803bytes, 현행 배정40회/41,943,040bytes. 최근30분 정리 작업 성공6회. 이 시점에는 새 상한 migration이 미적용이고 주행 기능 비활성 상태다.

외부 게시/적용 승인안은 용량 제한 migration과 안전한503 오류 전달, 회귀 검사, 운영 문서만 포함한다. `JOURNEY_WEATHER_ENABLED=false`, 현행40회/40MiB 배정과 Production은 그대로다. 상시 활성화·예산 증액은 별도 단계다. 공개 문서에 계정 키·회원 식별자·실제 경로·공유 토큰·로그 원본을 넣지 않는다.

복구: 새 경로를 비활성 상태로 유지하고 이 schema를 보존한다. 컬럼/원장을 삭제하거나 이전의 용량 제한 없는 RPC로 되돌리지 않는다. 만료 정리를 유지하고 물리 공간 때문에 차단되면 현재 크기·autovacuum 상태를 확인한다. 자동 상한 증가/유료 전환/전체VACUUM을 수행하지 않는다. 긴급 오류 전달 롤백은 기존 Edge bundle로 가능하지만 DB guard는 유지한다.
